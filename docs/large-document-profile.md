# Automatic large-document handling

Large spreadsheets and CSVs now use the standard APIs and CLI. No
`--large-documents` flag or retry is required. The parser uses row-based XML
processing and temporary storage where supported; Markdown output releases rows
as it writes them. Structured output returns the complete in-memory model.

```sh
bulkparse parse large.xlsx --output large.md
bulkparse parse large.xlsx --to json --output large.json
```

```rust,no_run
let parser = bulkparse::Parser::default();
let document = parser.parse_file("large.xlsx")?;
let summary = parser.parse_file_to_markdown("large.xlsx", "large.md")?;
# Ok::<(), bulkparse::Error>(())
```

```js
import {parseFile, parseFileToMarkdown} from '@bulkgrid/bulkparse';
const document = await parseFile('large.xlsx');
const summary = await parseFileToMarkdown('large.xlsx', 'large.md');
```

Choose the API for the representation you need; the examples demonstrate both,
and calling both parses twice. Rebuild native bindings after updating.

## Finite defaults and explicit limits

| Budget | Default |
| --- | ---: |
| Counted source/model nodes | 16,777,216 |
| Total table cells, including grid slots | 4,194,304 |
| Additional cells generated by row/column repetition | 100,000 |
| Expanded package bytes read | 256 MiB |
| Native writer Markdown, including markup | 128 MiB |
| Input bytes / extracted text | 32 MiB / 32 MiB |
| Depth / pages / archive entries | 64 / 2,000 / 10,000 |

The default node/cell/expansion ceilings now permit the complete-document workload
previously requiring the larger profile. This is an intentional default change,
combined with fewer XML passes, shared source metadata and compact writer storage.
It is not an unlimited parse or an automatic retry with increased limits.
**Explicit caller limits are honored as supplied.** Tiny ODF inputs cannot bypass
the separate repetition ceiling by requesting millions of copies of one cell.

Rust callers can select `Limits::conservative()` for the earlier 200,000-node,
100,000-cell and 64 MiB expansion budgets. Bindings can set those values explicitly
through `limits`. `Limits::large_spreadsheets()` and the hidden CLI
`--large-documents` flag remain compatibility aliases; neither is required.

## Memory and output contracts

These limits bound work, not process RSS. Input, sparse worksheet values and
formatting metadata still use memory. Full JSON retains the full document;
Node additionally creates JSON transport data and JavaScript objects. Streamed
Markdown is the lower-memory choice when a document object is unnecessary.
CLI JSON output uses a buffered serializer instead of allocating another complete
JSON string. Files are published atomically and existing destinations are preserved.

The optional process pool stages large responses in temporary files, releases the
worker model before sending, and decodes the response directly into typed objects.
It does not retain a full response-byte buffer or a second generic JSON tree.
Its default response ceiling is 1 GiB; custom lower ceilings remain enforced.
The pool's deadline, cancellation and worker-replacement behavior remains intact.

A successful result can still have fidelity warnings. The 112-document study
returns 112/112 by default, without resource-limit recovery: after the fidelity follow-up, 13 have complete
status and 99 retain formatting or content limitations. This is not a quality
leaderboard or a guarantee for every possible document. Browser/WASM capacity for
the oversized corpus has not been established by the native checks.
